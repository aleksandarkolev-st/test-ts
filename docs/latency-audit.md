# Live response latency audit

The current measurements use **gpt-6.1-sol, low reasoning, T24E390 output and no microphone**. Three fresh synthetic interviews ran for at least an hour each. Their [completed recording summary](evidence/completed-hour-measurements-v71.json) retains unanswered and erroneous turns:

| Interview | Recorded turns | Visible retained words | Median | Sample p95 | Maximum |
| --- | ---: | ---: | ---: | ---: | ---: |
| General | 55 | 55 | 8.92 s | 36.22 s | 64.86 s |
| Systems | 52 | 51 | 9.76 s | 36.17 s | 42.98 s |
| DSA | 49 | 48 | 12.30 s | 50.94 s | 78.63 s |

These are descriptive first-word timings from physical synthetic playback end to actual overlay visibility. The p95 column uses observed words only. The [all-trial calculation](evidence/all-trial-hour-word-latency-v71.json), retaining unanswered rows in the rank denominator, gives **36.22 s general, 39.36 s systems and 73.95 s DSA**. Missing words have no invented numerical latency. The missing systems response timed out; the missing DSA response had no native question job after a spoken "Why?".

The [full independent review audit](evidence/full-independent-review-audit-v71.json) verifies **64 cohorts and 338 judgments, with none pending**, including **108 correct, four incorrect and 44 incomplete answers across the 156 hour rows**. General recorded 43/55 correct, systems 35/52 and DSA 30/49. These are provisional independent model judgments against the spoken source question, with isolated reviewer history; they are not executable correctness certificates or population accuracy estimates. The [recorded findings](recorded-interview-findings-v71.md) and [requirement audit](evidence/measured-goal-scope-audit-v71.json) separate correctness, first-word delivery and the attached ten tests.

The [78.6-second DSA tail](evidence/algorithms-79-second-tail-decomposition-v71.json), bound to the completed journal, includes **35.16 s from confirmation to sending the final input**, 38.56 s from sending to matching reader receipt, 70 ms from reader receipt to consumer processing, 4.23 s to retained decoded text, and 7 ms to native visibility. The source still permits 120 seconds per generation attempt. There is no 50-second hard maximum.

A subsequent [completed 27-turn code-memory probe](evidence/completed-deep-memory-measurements-v71.json) ran for 49.3 minutes, recording 26 visible first words, one missing response and five errors. Its first-word median was 12.06 s, sample p95 93.93 s and maximum 95.43 s. The independently reviewed outcomes were fourteen correct, two incorrect, ten incomplete and one unverified. The [source-bound code checks](evidence/recorded-substantive-checks-v71.json) show that the original implementation was absent from selected context and was not reproduced at round 22 after twenty intervening turns. The answer requested the missing source. An appropriate clarification judgment does not satisfy the strict code-retention requirement; the evaluation interviewer also truncated its public reference to the original question.

The [93.9-second retained first word](evidence/deep-memory-94-second-tail-decomposition-v71.json) waited **41.19 s before final input submission**, followed by 50.03 s before matching reader receipt and 2.05 s before retained decoded text. This row also records `Codex answer timed out`; a visible word does not make it a successful answer. Its input timing and retained word [match the final stopped journal](evidence/deep-memory-final-checkpoint-bindings-v71.json).

The substantial pre-submission intervals demonstrate application scheduling delay. Reader receipt is an application timestamp, so the following interval combines provider work, transport and any preceding shared-reader blockage; it cannot be called isolated model compute. Per-thread completed queue waits do not exclude blockage on other threads. Large repeated prompts are recorded, but their causal cost has not been isolated.

The official [Codex App Server documentation](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn), checked on 2026-10-11, specifies that `turn/steer` appends input to the active turn and returns its accepted turn ID. It does not promise immediate replacement of inference. The same documentation describes `turn/interrupt` and a subsequent interrupted terminal status. The recorded waiting intervals establish the application's actual behavior; the documentation alone does not quantify provider latency.

The candidate on `fix/latest-question-wins` coalesces revisions locally, submits one complete frame per attempt, rejects obsolete output, and retires stale generation before a fresh replacement. Its 400 ms stale-work guard applies on every acknowledged attempt; further confirmed revisions do not extend it. Resumed speech waits for confirmation, and the stream allows at most three replacements. Terminal cleanup, literal references and explicit context are preserved. This is a universal protocol policy with no topic or expected-answer routing.

## Weaknesses and current action

1. **Repeated provisional generation and queued corrections.** The default driver used 0â€“6 steers and 0â€“5 follow-ups per question. Each obsolete generation can delay the final frame. Two four-waveform comparisons in opposite orders found that holding question-only refinements until confirmation made six of eight pairs faster: descriptive median 2,837.5 ms versus 2,027.5 ms. Different generated contexts and cloud calls prevent a causal claim. Separate text probes regressed, and every native sample still exceeded 800 ms. The experimental policy remains disabled in release. See [cross-order evidence](evidence/luna-refinement-comparison-v17.json).

2. **Retracted drafts fed back as reference context.** A failing runtime regression showed that resuming the same unfinished question cleared its buffer but retained its visible draft in meeting context. That could create a spurious context correction. Both continuation paths now forget only the resumed job's retracted suggestion. Earlier answers and exact displayed code for other questions remain available. The fix passed 102 library tests and the release build, and is in the workspace app. A causal latency improvement has not been demonstrated.

3. **Endpoint delay versus premature cuts.** Nemotron currently uses 510 ms endpoint history with 160 ms chunks. Final transcript receipt takes longer than that configured endpoint alone. Reducing either setting needs matched audio and clause-retention evidence: prior 80 ms chunk tests did not show a consistent first-output improvement. A learned endpoint classifier could help, but the evaluated audio-only classifier prematurely accepted internal pauses or rejected true ends. Adding another model request on the critical path would itself add latency. Reply intent is already classified by signed-in Luna in the same inference as the answer, without domain phrase routing.

4. **Microphone activity splits remote questions.** Two normal capture runs lost earlier clauses after microphone speech-start events interrupted the remote floor. This damages useful speculation and can trigger replacement requests. The cause of microphone activity is unproven. Remote-only capture isolates experiments; production still captures both channels. A change here must preserve genuine interruptions and avoid merging different speakers' turns.

5. **Growing exact answer history.** Selected meeting excerpts have budgets, but the two recent suggestions, retained complete implementation and visible unfinished suggestion can be much larger. Long code can increase input size and exhaust the reusable history budget, which suppresses intermediate refinements. This is a source-level risk, not measured starvation in the six-round run. Any reduction must preserve the exact code and constraints needed for follow-ups rather than silently truncate them.

6. **Repeated decoding and publishing.** The JSON reply decoder reparses accumulated text, and runtime publication clones the current snapshot on updates. These can become more expensive for long streamed code. They are lower-priority candidates: current rendering is about 10 ms, and no CPU profile has attributed the much larger post-consumption interval to them.

The assistant still fails some difficult reasoning questions on Luna low/Fast, including the final release-sequence question in this run. Faster first words alone would not satisfy the goal. The [independent review](evidence/luna-fast-review-v18.json) records the technical limitations. No scenario-specific answers or CUDA keyword fixes were added.
